# Synthetic Data Methodology

All data is fictional and generated by `data/generator` from an integer seed. The same seed always yields
byte-identical files; this is verified by tests.

## Observable vs. hidden

| Written to `dataset/` (importable) | Written to `ground_truth/` only (never imported or served) |
|---|---|
| components, ASIL, dependencies | `latent_fragility` per component |
| requirements with FMEA impact/occurrence/detectability | per-test detection `sensitivity` |
| builds and their component/requirement changes | every injected fault: component, build, variant scope |
| tests, requirement/component/variant links | whether and by which execution each fault was detected |
| executions actually run by engineers, verdicts, defects | |

## Fault process (hidden)

1. Each component draws `fragility ~ Beta(1.3, 4)`.
2. Per build, fault exposure is `base_rate·fragility + change_rate·magnitude·fragility`, and a fraction of it
   propagates to downstream dependents. The number of faults is Poisson-distributed.
3. Undetected faults survive into the next build with probability 0.6.
4. A selected test on an in-scope variant detects a live fault on one of its components with its hidden
   sensitivity, which is higher for HIL/vehicle tests than for SIL.
5. A detection creates a `FAIL` execution and a defect. Error codes are drawn from a small per-component pool,
   so failures recur and can be fingerprinted. Flaky failures and blocked runs add noise without defects.

## Why observable signals are imperfect on purpose

- **FMEA occurrence** mixes 30 % fragility signal with 70 % noise, modelling stale or subjective expert judgement.
  A test checks that the correlation stays between 0 and 0.8.
- **FMEA impact** follows ASIL, but high-impact components do not necessarily fail more often.
- 12 % of requirements have no linked test (structural gaps).

This makes risk-based ranking a real inference problem instead of a formula lookup.

## Historical engineer selection

For each build, roughly 55 % of applicable (test, variant) pairs are run. The ranking behind that choice uses
requirement severity (0.45), habit (ran last build, 0.30), automation (0.15) and randomness (0.25). It is
deliberately a plausible but imperfect human baseline for shadow test planning.
